4. 并行模式：归约、扫描与模板计算

前一章讲“怎么把数据搬对”，这一章讲“怎么把算法摆成 GPU 的形状”。核心思想只有一句：把串行的累加改成树形，把跨线程的依赖换成每一层同时完成。代价是总工作量变大、结果不再逐位可复现。

4.1 归约：从 O(n) 步到 O(log n) 步

串行求和需要 \(n-1\) 次加法、\(n-1\) 步。树形求和的第一层让 \(n/2\) 对元素同时相加，第二层 \(n/4\) 对，依此类推，总共仍是 \(n-1\) 次加法（工作量不变），但关键路径长度从 \(n\) 降到 \(\log_2 n\)。GPU 有几千个并行单元，正好把这个深度摊开。

一个 block 内可以完全用寄存器 + shuffle 完成，不碰 shared：

reduce.cu

__inline__ __device__ float warpReduce(float v) {
    #pragma unroll
    for (int off = 16; off > 0; off >>= 1)
        v += __shfl_down_sync(0xffffffffu, v, off);
    return v;                                  // lane 0 拿到整个 warp 的和
}

__global__ void blockSum(const float* x, float* out, int n) {
    __shared__ float partial[32];              // 每 block 最多 32 个 warp
    int tid = threadIdx.x;

    float v = 0.0f;
    for (int i = blockIdx.x * blockDim.x + tid; i < n; i += blockDim.x * gridDim.x)
        v += x[i];                             // 先做串行部分，尽量少用 shuffle

    v = warpReduce(v);
    if ((tid & 31) == 0) partial[tid >> 5] = v;
    __syncthreads();

    if (tid < 32) {
        int nwarps = blockDim.x >> 5;          // 这里假设 blockDim 是 32 的倍数
        v = (tid < nwarps) ? partial[tid] : 0.0f;
        v = warpReduce(v);
        if (tid == 0) atomicAdd(out, v);       // 每个 block 一次原子
    }
}

三个设计点：

  • 先串行、后并行。每个线程在 grid-stride 循环里已经把多次加法做掉了，shuffle 只处理“每个线程一个值”的最后一层。反过来（每个元素都 shuffle）会浪费指令。
  • 两级归约。warp 内用 shuffle，warp 之间用 shared。这是 GPU 归约的标准骨架。
  • 跨 block 汇总。atomicAdd 最简单，但顺序不定、结果不可复现。要确定性就写两阶段：kernel 1 把每个 block 的部分和写进数组，kernel 2 再归约那几千个数。

上一版代码里 atomicAdd 的浮点结果每次都可能差几个 ULP，因为 block 的完成顺序由调度决定。这和 CPU 上多线程累加的问题一模一样；需要复现实验时，用固定的两阶段版本，或改用 double/Kahan 累加。

4.2 扫描：每个位置都要前缀和

给定 \(x_0,\dots,x_{n-1}\)，扫描要输出

\[ y_i = \sum_{j=0}^{i} x_j . \]

串行是 \(n\) 步。Hillis-Steele 的并行版本在每一轮让每个位置加上它前面 \(2^{d}\) 个位置的当前值：

scan.cu

// 单 block，要求 blockDim.x == n，动态 shared 传入 n 个 float
__global__ void scan(float* x, int n) {
    extern __shared__ float s[];
    int t = threadIdx.x;
    s[t] = (t < n) ? x[t] : 0.0f;
    __syncthreads();

    for (int off = 1; off < n; off <<= 1) {
        float add = (t >= off) ? s[t - off] : 0.0f;
        __syncthreads();          // 先让所有人读完上一轮
        s[t] += add;
        __syncthreads();          // 再让所有人写完，供下一轮读
    }

    if (t < n) x[t] = s[t];
}

启动：scan<<<1, n, n * sizeof(float)>>>(d_x, n)。复杂度是 \(O(n\log n)\) 次加法——比串行多做了 \(\log n\) 倍的工作，但深度只有 \(\log n\)。GPU 的并行度高，这个交换通常是划算的。Blelloch 的上行/下行两趟可以把工作量降回 \(O(n)\)，代价是常数更大、实现更绕；生产代码直接用 CUB 的 DeviceScan。

扫描是很多算法的地基：stream compaction（把满足条件的元素挤到前面）、稀疏矩阵组装、排序的基数排序阶段，都要它。

4.3 模板计算：halo 与 shared

一维卷积、差分、平滑都属于 stencil：每个输出依赖输入的一个邻域。把邻域搬进 shared，一次加载、多次复用：

blur.cu

constexpr int R = 4;                       // 半径，窗口 2R+1

__global__ void blur1d(const float* in, float* out, int n) {
    extern __shared__ float s[];           // 大小 = blockDim.x + 2R
    int base = blockIdx.x * blockDim.x;

    for (int j = threadIdx.x; j < blockDim.x + 2 * R; j += blockDim.x) {
        int g = base - R + j;              // 带 halo 的全局下标
        s[j] = (g >= 0 && g < n) ? in[g] : 0.0f;
    }
    __syncthreads();

    int g = base + threadIdx.x;
    if (g < n) {
        float acc = 0.0f;
        #pragma unroll
        for (int k = -R; k <= R; ++k) acc += s[threadIdx.x + R + k];
        out[g] = acc / (2 * R + 1);
    }
}

边界处理是这类 kernel 的主要工作量：halo 超出数组时补 0、复制边缘或跳过。二维 stencil 的复用率更高——每个 block 加载 \((T+2R)^2\) 个元素，服务 \(T^2\) 个输出，算术强度随 \(T\) 线性增长。

4.4 直方图：原子冲突与私有化

最直接的直方图是每个元素对全局数组做一次 atomicAdd。256 个 bin、几百万个元素时，热点地址会被反复争用。标准解法是“每个 block 一份 shared 副本，最后合并”：

hist.cu

__global__ void histogram(const unsigned char* data, int n, unsigned int* hist) {
    __shared__ unsigned int local[256];
    for (int i = threadIdx.x; i < 256; i += blockDim.x) local[i] = 0;
    __syncthreads();

    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += blockDim.x * gridDim.x)
        atomicAdd(&local[data[i]], 1u);        // 打在 shared 上，不抢全局
    __syncthreads();

    for (int i = threadIdx.x; i < 256; i += blockDim.x)
        if (local[i]) atomicAdd(&hist[i], local[i]);
}

shared 上的原子仍然会在“多个 lane 命中同一个 bin”时串行化，但比全局原子便宜一个数量级，而且冲突被限制在一个 block 内。如果数据分布非常集中（比如 90% 都是 0），可以再复制几份 local[K][256]，按 threadIdx.x % K 选副本，最后合并，用空间换冲突。

注意 hist 必须在 host 侧清零（cudaMemset），kernel 只做累加。

4.5 work / span：为什么 GPU 愿意“多干活”

并行算法的两个量：work \(W\) 是总操作数，span \(S\) 是关键路径长度。用 \(p\) 个执行单元时，下界是

\[ T_p \;\ge\; \max\left(\frac{W}{p},\; S\right). \]

CPU 上 \(p\) 小（几十），所以优化 \(W/p\) 更重要；GPU 上 \(p\) 大（几万），\(W/p\) 很快降到 1 以下，span 变成瓶颈。这解释了为什么 Hillis-Steele 扫描（\(W=O(n\log n)\)）在 GPU 上仍然常用：它把 span 压到 \(O(\log n)\)，而多出来的工作量被几千个 lane 摊掉了。

4.6 容易写错的地方

常见错误
  • shuffle 的 mask 写死全 1。最后一个 warp 只有部分 lane 活跃时，结果是未定义；按 __ballot_sync 或实际 blockDim 计算 mask。
  • 假设 blockDim.x 是 32 的倍数。归约里 nwarps = blockDim.x >> 5、partial[tid >> 5] 都依赖这个假设。
  • 忘记处理尾块。grid-stride 循环能兜住 \(n\) 不是 block 整数倍的情况，但 stencil 的 halo 和扫描的 t < n 仍要单独判。
  • 归约的初值写错。求和初值 0、求 max 初值 -INFINITY，不要把“线程没数据”当成 0 参与 max。
  • 用原子汇总浮点后要求逐位复现。顺序不定，结果不定；要复现就固定树形结构。
  • shared 大小按“每线程一个”估。归约的第二级只需要 32 个 float；histogram 需要 256 个 bin × 副本数。
