7. 视觉路径：一张图怎么变成 602 个 token

7.1 bllm 的 token embedding，换成图像 patch

bllm 2.7 节做的事是：把每个 token id 查表得到一个 1024 维向量，序列就变成了一个矩阵，送进 Transformer。视觉分支做的是同一件事，只是"词表"换成了"图像块"：把图切成 \(14\times14\) 的小块，每块展平后线性投影成一个向量，然后把这些向量当 token 送进一个 32 层的 Transformer。

整条路径（以 \(1008\times1008\) 的图为例）：

图像 1008 x 1008
  patch 14     网格 72 x 72
  5184 个 patch x 588 维
  ViT 32 层    图内交互
  3x3 重排     网格 24 x 24
  576 个 token x 9216
  2 层 MLP     576 x 5120
  加 24 个行标记 + 首尾 2 个
  = 602 个位置进主干

注意最后一步：视觉 token 不是直接拼进文本的，中间还要插行标记（IMAGE_NEW_LINE）和起止标记（IMAGE_START／IMAGE_END）。原因很直接：把二维网格压成一维序列之后，模型就不该再"知道"哪些 token 原本在同一行，除非你告诉它。行标记就是这个告知。

7.2 预算公式：为什么是 602，不是 576

设预处理后的像素高宽为 \(H\times W\)，patch 边长 \(p=14\)，空间合并因子 \(r=3\)（下节讲）。依次算：

\[ h=\frac{H}{p},\qquad w=\frac{W}{p}, \]

这是 patch 网格的行列数。合并时网格未必能被 3 整除，所以先在右侧和底部补零维到整数倍：

\[ \bar h=r\left\lceil\frac{h}{r}\right\rceil, \qquad \bar w=r\left\lceil\frac{w}{r}\right\rceil . \]

合并后的网格与其内容 token 数：

\[ h'=\left\lceil\frac{h}{r}\right\rceil, \qquad w'=\left\lceil\frac{w}{r}\right\rceil, \] \[ N_{\text{visual}}=h'w' . \]

而真正要算进上下文预算的是"span"——每行末尾一个行标记，再加首尾两个：

\[ N_{\text{span}}=h'(w'+1)+2=N_{\text{visual}}+h'+2 . \]

回到 \(1008\times1008\)：\(h=w=72\)，\(h'=w'=24\)，于是 \(N_{\text{visual}}=576\)，\(N_{\text{span}}=24\times25+2=602\)。那 26 个位置全是标记——占 4.3%，但忘了它就会算错预算。

判断方法

预算的分母是 \(N_{\text{span}}\) 而不是 \(N_{\text{visual}}\)，上限是 vision_max_n_token=1024。所以"最多能放多少视觉点"要解 \(h'(w'+1)+2\le1024\)，不是 \(h'w'\le1024\)。

7.3 三个算例：预算到底怎么卡住尺寸

例一（方形最难的那一档）：\(1344\times1344\) 时 \(h=w=96\)，\(h'=w'=32\)，\(N_{\text{visual}}=1024\)，但 \(N_{\text{span}}=32\times33+2=1058>1024\)。内容刚好 1024，加上标记就超了。报告里的处理是重算一个更小的画布：取 \(31\) 组，即

\[ 31\times3\times14=1302 , \]

得到 \(N_{\text{visual}}=961\)、\(N_{\text{span}}=31\times32+2=994\)，留出 30 个位置的余量。这就是"支持约 \(1344\times1344\)"的实际含义：理论边界是 1344，实际落点是 1302。

例二（非方形）：\(1920\times1080\) 先按原尺寸算：高 1080 → 26 行，宽 1920 → 46 列，\(N_{\text{span}}=26\times47+2=1224>1024\)，必须缩。缩到 \(1708\times966\) 后：行 \(\lceil966/42\rceil=23\)，列 \(\lceil1708/42\rceil=41\)，\(N_{\text{visual}}=943\)，\(N_{\text{span}}=23\times42+2=968\)。这里 \(1708/14=122\) 不能被 3 整除，所以特征网格右侧补 1 列到 123，再分成 41 组。

例三（小于最小面积）：原图面积小于 \(544^2=295{,}936\) 时先放大，否则一张小图会被切成太少的 patch，视觉 token 数量不足以表达内容。放大后再走上面的对齐与预算检查。

画布          h'x w'   N_span
1008 x 1008   24x24      602
1344 x 1344   32x32     1058 超
1302 x 1302   31x31      994
1920 x 1080   26x46     1224 超
1708 x  966   23x41      968

7.4 patch embedding：为什么是线性投影

切块之后，一张 \(1008\times1008\) 的 RGB 图变成 \(72^2=5184\) 个块，每块 \(3\times14\times14=588\) 个数。把每块展平成一个 588 维向量，堆成矩阵 \(U\in\mathbb{R}^{5184\times588}\)，然后乘一个共享的权重：

\[ X^{(0)}=UW_p+b_p, \qquad W_p\in\mathbb{R}^{588\times1024}, \] \[ b_p\in\mathbb{R}^{1024}. \]

所有块共用同一组权重——这正是卷积的"权重共享"，而一个 \(14\times14\) 步长的卷积在原图上的效果与这个线性投影完全等价。报告的取舍是显式写成线性投影，理由是确保与 Muon 优化器兼容：Muon 对新矩阵参数做正交化更新，卷积核的形状与前缀让它不好处理，摊平成矩阵就统一了。

顺带说一句归一化：像素先按

\[ x=\frac{I/255-0.5}{0.5}=\frac{2I}{255}-1 \]

映射到 \([-1,1]\)，与 bllm 2.7 节对 token 做 embedding 之前的那一步是同一类操作，只是这里的"字"是像素。

7.5 ViT：32 层双向注意力

接下来 32 层视觉 Transformer，输入输出都是 \(5184\times1024\)。每层和 bllm 4.5 节的块同构：RMSNorm → 注意力 → 残差，RMSNorm → 前馈 → 残差，最后整个塔末再归一化一次。差别有三处：

  • 双向，不是因果。图像没有"未来"，所以不掩码；这对应 bllm 第 1 章讲的 encoder 侧用法。
  • 16 个头、每头 64 维。QKV 一个线性层出 \(3\times1024=3072\) 维，再切成 16×64。
  • 2D RoPE。位置编码作用在 Q、K 上（不作用在 V），用的是 patch 的 \((i,j)\) 二维坐标，而不是一维的 \(t\)。所以"上面的块"和"左边的块"是不同的相对方向——这是图像里必须区分的信息。

前馈是 SwiGLU：先投到 \(5632=2\times2816\) 维并拆成两支，一支过 SiLU 当门，与另一支逐元素相乘，再投回 1024。\(2\times2816\) 这个"两倍"就是 bllm 4.3 节 SwiGLU 的门控结构，不重复推。

7.6 3×3 重排：把 9 个 patch 拼成一个 token

32 层之后，每个 patch 都已经"看过"整张图（双向注意力），所以相邻 9 个 patch 的表示是高度冗余的。重排就是把 9 个相邻的 1024 维向量首尾拼成一个 9216 维向量：

\[ 24\times24\ \text{网格},\quad 576\ \text{个位置}, \] \[ 576\times(9\times1024)=576\times9216 . \]

这次拼接没有信息损失（9216 维装下了 9 个 1024 维向量），真正的压缩发生在下一步的两层 MLP：

\[ 576\times9216\ \longrightarrow\ 576\times5120 . \]

也就是 \(9216\to5120\)，把 9 个 patch 的信息压进一个主干宽度的向量。整个流程的压缩比是：

\[ \frac{5184}{576}=9, \qquad \frac{9\times1024}{5120}=1.8 , \]

第一个比值是位置数（9 个 patch 合成 1 个位置），第二个是每个位置的宽度（9216 维压到主干宽度 5120）。位置数降 9 倍才是主要收益：\(1008^2\) 的图从 5184 个候选位置变成 602 个，和文本侧一段一万字的上下文是同一个量级。

为什么敢压 9 倍？因为 ViT 的 32 层已经把图内交互做完了。如果先把图切成 9 倍少的 token 再做注意力，每个 token 就只能看到自己那一小块，远处的物体关系学不到。顺序很重要：先在高分辨率网格上做交互，再降采样进语言主干。

7.7 多模态的 MoE 负载均衡

第 6.2 节说 MoE 是 384 选 6。多模态带来一个新问题：图像 token 和文本 token 的表示分布不同，会各自偏好不同的专家；如果只维护一份全局的逐专家偏置，两种模态之间的负载差异会被平均掉，各自内部的不均衡反而看不出来。

报告的做法是为文本与图像各维护一组逐专家校正偏置：路由时按 token 所属模态取对应的偏置做选择，但权重仍用原始路由分数（偏置只影响"选谁"，不影响"选上之后给多少权重"）；每个训练步按各自模态的负载独立更新两组偏置。这和 bllm 里无辅助损失的负载均衡是同一个思路，只是把"一份偏置"换成了"每个模态一份"。

7.8 容易算错的地方

常见错误
  • 用 \(N_{\text{visual}}\) 当预算。上限 1024 卡的是 \(N_{\text{span}}=N_{\text{visual}}+h'+2\)，差的就是行标记与首尾。
  • 以为 1344×1344 能进。它内容恰好 1024，加上 34 个标记就 1058，超了；实际落点是 1302（31 组）。
  • 把重排当成"信息压缩"。9 个向量拼成 9216 维时没损失，压缩发生在 9216→5120 的 MLP 里。
  • 算行标记数量用 \(w'\)。每行一个，所以是 \(h'\) 个（行数），不是列数。
  • 把视觉注意力也当因果。ViT 内是双向的，掩码只在语言主干里。
